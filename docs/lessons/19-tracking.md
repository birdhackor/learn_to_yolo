# 19 簡易 tracking：框很準，ID 仍可能換人

[在 Colab 執行本節](https://colab.research.google.com/github/birdhackor/learn_to_yolo/blob/lessons-v0.4.0/notebooks/19-tracking.ipynb){ .md-button }

偵測只回答「這一幀（frame，影片裡的一張畫面）有哪些框」。追蹤（tracking）還要回答：這一幀的某個框，是否和上一幀的某個框是同一個物件？本節要讓你看到：兩個同類物件交叉時，偵測可以完全正確，追蹤給的編號（track ID）卻互換了。讀完本節，你能手算一個小型 tracker（追蹤器）每一幀怎麼配對，也能自己數出 ID 換了幾次。你也會知道：只看上一幀的框為什麼會換號，先用速度預測位置為什麼不會。

前置是 6.2 [偵測評估](06-evaluation.md) 用到的 IoU（交集面積÷聯集面積）與一對一配對，以及第 18 章[影片管線](18-video.md)的逐幀處理。

本節反覆用到三個詞：

- track（軌跡）：tracker 替每個正在追的物件保存的一筆紀錄，有四個欄位：編號 `id`、最後一次配到的框 `box`、速度 `velocity`（框的四個座標每幀各移動幾畫素）、最後一次配到的幀號 `last_frame`。track ID 就是這筆紀錄的編號；同一個物件每一幀都應該拿到同一個 track ID。
- association（關聯）：把這一幀的偵測框接到既有的 track 上，也就是本節說的「配對」。它和 6.2 評估時的配對（matching）一樣用 IoU、一對一，但目的不同：評估是拿預測框和真值框（GT）配對，這裡沒有 GT 參與。
- ID switch（身份換號）：評估時用真實身份檢查。同一個物件這次被偵測到時拿到的 track ID，和它上次被偵測到時不同，就算 1 次；中間漏檢的幀跳過，跟更早那次比。兩個物件互換編號時，兩個物件各算 1 次，共 2 次。

本節比較兩種配對方法，兩者吃同一組偵測框：

- 上一框法：直接拿每條 track 最後一次配到的框，和這一幀的偵測框算 IoU。程式裡是 `motion=False`，印出的結果標 `last-box IoU`；圖上也寫「上一框法」。
- 速度預測法：先用速度推算物件這一幀應該在哪裡，再拿推算出的框算 IoU。程式裡是 `motion=True`，印出的結果標 `velocity IoU`；圖上也寫「速度預測法」。

本節只做追蹤最核心的配對規則，不是完整的實用追蹤器。主案例的框是人工給的，沒有跑偵測模型，連第 4 幀的一次漏檢也是刻意安排的；兩種方法吃完全相同的框，所以兩者結果的差別只來自配對規則，不會混進真實偵測器那種無法控制的錯誤。到頁末「接上真正的逐幀預測」那一小節，才接上第 18 章 MiniYOLO 偵測模型的真實輸出。

tracker 看不到真實身份 A、B；A、B 只在最後評估時，用來判斷哪個物件換了 track ID。A、B 也設成同一類別，避免只靠類別標籤就分出誰是誰。常見的完整追蹤器和正式評估指標，集中在後面「收益、代價與失敗範圍」的摺疊區說明。

## 六幀，兩個物件與一次漏檢

兩個框都是寬 12、高 12，y 範圍 20 到 32，單位是畫素。框寫成 xyxy，也就是 [x1, y1, x2, y2]：左上角與右下角的座標。第 f 幀 A 的 x1 為 `16+8f`，B 為 `40−8f`；每幀 A 向右移 8、B 向左移 8。到第 2 幀，A、B 的左右順序已經反過來。第 4 幀 B 其實還在，但人工偵測序列故意不給 B 的框，模擬偵測器漏檢；第 5 幀 B 的框再出現。程式裡，`truth_boxes(f)` 寫出第 f 幀兩個物件的真值框（六幀都有 A、B）；`frames()` 從這些真值框取出每一幀的偵測框，只在第 4 幀拿掉 B。每一幀的偵測框都照 A、B 的順序排（第 4 幀只有 A）。

| 幀 f | 0 | 1 | 2 | 3 | 4 | 5 |
| --- | --- | --- | --- | --- | --- | --- |
| A 的 x1 | 16 | 24 | 32 | 40 | 48 | 56 |
| B 的 x1 | 40 | 32 | 24 | 16 | （漏檢） | 0 |

## tracker 每一幀做什麼

tracker 記住的是一串 track，外加下一個要發的 ID。每一幀呼叫一次 `tracker.update(boxes, frame)`，傳入這一幀的偵測框和幀號；它回傳每個偵測框拿到的 ID。下表的 T 是目前保留的 track 數，D 是這一幀的偵測框數；第 0 幀還沒有任何 track，T=0。

| 資料 | shape | 用途 |
| --- | --- | --- |
| 這一幀的偵測框 | `[D,4]`，畫素座標 xyxy | D 通常是 2，第 4 幀是 1，也可以是 0 |
| 各 track 的待配對框 | `[T,4]` | 拿來和偵測框比 IoU 的框：上一框法用上次的框，速度預測法用預測框 |
| IoU 矩陣 | `[T,D]` | 每條 track 和每個偵測框的重疊程度，用來決定誰配誰 |
| association IDs（update 的回傳值） | 長度 D 的整數 list | 依這一幀偵測框的順序排（本例即 A、B） |

update 依序做五件事：

1. 刪掉太久沒配到的 track：間隔 `frame - last_frame`（這一幀和上次配到那一幀的幀號差）大於 max_age 的 track，直接刪除。max_age 是間隔允許的最大值，後面再說明。
2. 算每條 track 的待配對框：上一框法直接用 `box`；速度預測法用 `box + velocity * (frame - last_frame)`，也就是速度乘上間隔。
3. 算 `[T,D]` 的 IoU 矩陣，做一對一配對；IoU 低於 0.1 的組合不准配。怎麼配，後面再說明。
4. 配到的 track 先更新速度：速度=(新框−舊框)÷間隔。再把 `box` 換成新框、`last_frame` 換成這一幀。
5. 沒配到的偵測框，依順序各開一條新 track，速度設為 0。新 ID 從 1 開始依序往上加，刪掉的編號不會再發。

照這個順序走一遍。第 0 幀沒有任何 track，兩個框都配不到，A 先拿 ID1、B 拿 ID2，速度都是 0。第 1 幀兩條 track 的速度還是 0，速度預測法的待配對框就是上次的框，所以兩種方法在第 1 幀的結果相同。第 1 幀配完，才算出 A 的速度 (24−16)÷1=8；四個座標合起來是 `[8,0,8,0]`（畫素／幀），B 是 `[-8,0,-8,0]`。

第 1 幀為什麼配得上？每幀移動 8 畫素、框寬 12，相鄰兩幀的同一物件只重疊 4 畫素寬。交集是 4×12=48，兩框面積都是 12×12=144，所以 IoU=`48/(144+144−48)=.2`。第 3 步的 IoU 門檻，就是拿這種重疊（track 的待配對框對偵測框）去比。由這個數字可以推出：門檻若高於 0.2，例如 0.5，第 1 幀兩個物件都配不上，會全部開新 ID；本例的門檻是 0.1，低於 0.2，所以配得上。

沒配到的 track 不會馬上刪，會暫時留著，直到間隔大於 max_age；本節 `max_age=2`。所以 B 的 track 在第 3 幀配到、第 4 幀漏檢，第 5 幀的間隔是 5−3=2，沒有大於 2，track 還留著，有機會接回。換句話說，max_age=2 最多只容許連漏 1 幀：假如 B 連漏第 4、5 幀，到第 6 幀間隔是 3，B 的 track 在配對前就被刪了。物件只消失一幀，tracker 不會馬上丟掉它的身份。

## 配對要一對一，也要允許不配

第 3 步的配對有兩條規則。第一是一對一：一條 track 最多配一個框，一個框也最多配一條 track。第二是允許不配：第 4 幀只有 1 個框，卻有 2 條 track，一定有一條配不到；物件剛出現或剛消失時，也會有框或 track 找不到對象。

程式把所有可能的配法全部列出來比較，這叫列舉。每條 track 可以選「不配」，或選一個還沒被用掉、而且合格（IoU 至少 0.1）的偵測框。以 2 條 track、2 個框、四個 IoU 都合格為例，共有 7 種配法（track 和框都從 0 開始編號）：

- 都不配：1 種。
- 只配一對：4 種（2 條 track 選 1 條，2 個框選 1 個）。
- 配兩對：2 種。直配是 track 0 配框 0、track 1 配框 1；交叉是 track 0 配框 1、track 1 配框 0。

程式把每一種都算一遍，先挑配成功對數最多的；對數一樣多，再挑 IoU 總和最大的。「先比對數」是本節的簡化選擇。完整列舉一定找得到這個規則下的最佳解，但配法數會隨物件數暴增，只適合本例這麼小的情況；正式系統的做法見這一小節最後兩段。沒有任何偵測框時，它回傳空的配對清單。

update 第 2、3 步的核心可以寫成下面三行。這是示意，變數名和完整程式不完全相同：

```python
# 每條 track 各算一個 predicted_box，疊成 [T,4] 的 predicted_boxes；上一框法直接用 last_box
predicted_box = last_box + velocity * (frame - last_frame)
quality = iou_matrix(predicted_boxes, detections)  # [T,D]
# gated：IoU 低於 threshold 的組合不准配
# pairs 是 (track 列, 偵測欄) 的清單，例如 [(0,1),(1,0)]
pairs = exact_gated_matching(quality, threshold=.1)
```

`[(0,1),(1,0)]` 表示 track 0 配框 1、track 1 配框 0，也就是交叉配對。這裡的 0、1 是 IoU 矩陣的列號和欄號，不是 track ID。

本節的列舉不是貪心法。貪心法每一步先拿眼前最大的 IoU，拿了就不再改；它不保證 IoU 總和最大，反例見下方摺疊區。

??? note "為什麼不用貪心法"

    貪心法在 [13.1](13-dual-assignment.md) 介紹過。完整程式準備了一組會讓貪心法選錯的框：兩條 track 的框是 `[2,0,12,10]` 與 `[6,0,16,10]`，兩個偵測框是 `[3,0,13,10]` 與 `[0,0,10,10]`。這四個 IoU 是由真的框算出來的，不是隨手填的數字，約為 `[[.8182,.6667],[.5385,.25]]`（列是 track，欄是偵測框）。

    貪心法先配最大的 0.8182（track 0 配框 0），剩下只能配 0.25（track 1 配框 1），總和 1.0682。交叉配對（track 0 配框 1、track 1 配框 0）的總和是 `.6667+.5385=1.2052`，比較大。所以每一步拿最大值，不保證總和最大；本節才用完整列舉。完整程式用斷言（assert）確認：列舉選到的是交叉配對，而且交叉的總和比直配大。

列舉的配法數漲得很快：全部合格時，2 條 track 對 2 個框有 7 種，10 對 10 約 2.3 億種。正式系統改用專門解一對一配對的演算法，例如匈牙利演算法（Hungarian algorithm），不必把所有組合列出來；本節的列舉不是這種演算法。

正式系統處理「不配」常見兩種做法：SORT 先用匈牙利演算法配完，再剔除 IoU 低於門檻的配對；ByteTrack 的官方程式則把「不配」的代價放進配對問題本身，讓演算法在 IoU 太低時寧可不配。兩種做法的結果不一定相同。匈牙利演算法找的是總分最好的一對一配對，和本節「先比對數」的規則不完全一樣，結果也不一定相同。這類一對一配對問題，英文叫 assignment problem（指派問題）；這裡的 assignment 指配對問題，不是第 5 章、12.3 訓練時決定哪個預測負責哪個 GT 的 assignment。

## 為什麼上一框法會追錯

第 1 幀 A 的框在 x=24 到 36，B 在 32 到 44；第 2 幀 A 移到 32 到 44，B 移到 24 到 36。上一框法拿各 track 上一次的框來比。ID1 的上一框是 A 在第 1 幀的 24–36，和 B 在第 2 幀的 24–36 完全重合，IoU=1；ID2 的上一框 32–44，也和 A 的新框完全重合。正確身份反而只重疊 4 畫素寬，IoU 只有 0.2。

第 2 幀上一框法的 IoU 矩陣（列是 ID1、ID2，欄是 A、B）是 `[[0.2, 1], [1, 0.2]]`。兩種配法都配成兩對，於是比 IoU 總和：交叉配對 1+1=2，正確配對只有 0.2+0.2=0.4，所以上一框法選了交叉。兩個 ID 就這樣被交換，框本身卻沒有錯。

速度預測法在第 1 幀配完後，已估出 A 的速度 `[dx1,dy1,dx2,dy2]=[8,0,8,0]`、B 為 `[-8,0,-8,0]`。第 2 幀先用速度預測位置：ID1 預測到 32–44，ID2 預測到 24–36，正好和正確身份的新框重合。IoU 矩陣變成 `[[1, 0.2], [0.2, 1]]`，正確配對的總和是 2，所以不交換。B 漏掉第 4 幀後，第 5 幀的間隔是 2，速度要乘上 2：從第 3 幀的位置 16 預測到 16−8×2=0，正好是 B 第 5 幀的位置，所以仍能接回 ID2。

速度要乘上間隔，不能只加一次。不過在本例，只加一次也剛好接得上：預測 x1=16−8=8，框是 8 到 20，和 B 實際的 0 到 12 仍重疊 4 畫素，IoU=0.2，剛好過 0.1 的門檻，只是位置已經偏了 8 畫素。偏差=速度×(間隔−1)，漏得越久偏得越多。

看一個假想的情境（本節程式沒有這個情境）：B 連漏第 4、5 幀，第 6 幀才再出現。這時 max_age 要設 3，B 的 track 才不會在第 6 幀一開始就被刪。乘上間隔 3，預測 x1=16−8×3=−8，正好是 B 第 6 幀的位置（40−8×6=−8）。只加一次則預測 x1=8，偏了 16 畫素，比框寬 12 還大，兩框完全不重疊，IoU=0，B 就接不回來，只能開新 ID。

上一框法在第 5 幀仍保留舊的 ID1：它最後在第 3 幀配到 B，框是 `[16,20,28,32]`；間隔 5−3=2，沒有大於 max_age，所以還在。B 這一幀的偵測框是 `[0,20,12,32]`，兩框 IoU=0，低於 0.1，所以舊 ID1 和 B 的偵測框都沒配到（unmatched），B 只好開新的 ID3。第三次換號不是因為舊 ID1 過期：`max_age=2` 只讓舊 track 留下來當候選，要接回仍須通過 IoU 門檻。

![同一組偵測框的實際 ID 分配：上列為上一框法，下列為速度預測法](../assets/diagrams/19-tracking.svg)

圖分上下兩列：上列是上一框法，下列是速度預測法，列標題寫著各自的 ID 切換次數（也就是 ID switch 數）；每列 6 格，依序是第 0 到第 5 幀。每一格裡，A 畫在上半、B 畫在下半，只是讓字不重疊；「A：ID1」這類標籤，寫在各自方塊那一排的上方、靠格子左邊。兩框實際的 y 都是 20 到 32，配對時用的也是這個 y；水平位置則照真實的 x 等比例畫。

方塊的顏色代表 track ID，不是類別：紅色是 ID1、藍色是 ID2、紫色是 ID3。上列第 2 幀 A、B 互換顏色（A、B 各換 1 次），第 5 幀 B 變成紫色（再換 1 次），就是那 3 次換號；第 4 幀的「B：漏檢」表示 B 沒被偵測到。下列的顏色從頭到尾都沒變。

下面兩串數字是 update 實際回傳的 IDs。外層第 f 個（從 0 數起）是第 f 幀；內層依該幀偵測框的順序，列出各框拿到的 track ID。本例每幀的偵測框都照 A、B 排（第 4 幀只有 A），所以 `[2,1]` 表示 A 拿到 ID2、B 拿到 ID1。

- 上一框法：`[[1,2],[1,2],[2,1],[2,1],[2],[2,3]]`
- 速度預測法：`[[1,2],[1,2],[1,2],[1,2],[1],[1,2]]`

依開頭的定義，逐個物件數 ID switch。上一框法：A 依序拿到 1、1、2、2、2、2，在第 2 幀換 1 次；B 依序是 2、2、1、1、（第 4 幀漏檢，跳過）、3，在第 2 幀和第 5 幀各換 1 次；合計 3 次。速度預測法：A 一直是 1、B 一直是 2，共 0 次。

兩種 tracker 吃的是同一組人工偵測框，偵測本身的好壞對兩者完全一樣。程式另用 `evaluate_detections()` 替這組偵測框評分，不經過 tracker：每一幀的偵測框和 `truth_boxes(f)` 的兩個真值框做評估配對（matching），判定標準和 6.2 相同：IoU 至少 0.5 才算配上（配對 IoU 門檻 0.5），而且一對一，每個真值框最多配一個偵測框，反過來也一樣；配上的偵測框是 TP（正確偵測），沒配上的是 FP（誤報）。

這組人工框沒有 score，沒辦法照 6.2 那樣依 score 由高到低逐筆配；程式用的是本節的完整列舉 `exact_gated_matching`，門檻設成 0.5（tracker 配對時用的是 0.1）。本例 11 個偵測框都和自己的真值框完全重合（IoU=1），和另一個物件的真值框 IoU 最多 0.2，所以就算照 6.2 那樣一次處理一個框，不論先處理哪個框，結果也一樣：TP=11、FP=0。6 幀×2 個物件=12 個真值框，其中 11 個配上，所以偵測的 recall（真實物件被偵測到的比例）是 11/12；沒配上的就是第 4 幀的 B。ID switch 從 3 降到 0，全靠 tracker 換了配對方法，不是偵測變好。這也不是完整的多物件追蹤（MOT，Multi-Object Tracking）評估：本節只數 ID switch，沒有計算 IDF1、HOTA 等正式指標（說明見「收益、代價與失敗範圍」的摺疊區）。

執行 `PYTHONPATH=. python lesson_cases/19-tracking.py`（Colab 則執行「本節可修改的完整實驗」那一格），核對印出的兩份 IDs、switch 數 3→0，以及 `detector recall=11/12, false positives=0`。輸出倒數第二行的意思是「完整列舉通過了貪心反例與空偵測框兩項檢查」；程式先跑完所有斷言（assert）才開始印，所以看得到這一行，就表示這兩項檢查都通過了。recall 那一行也一樣：`evaluate_detections()` 依序回傳 TP、真值框數、FP，程式先用斷言確認它們是 `(11, 12, 0)`，才印出來。tracking 規則不是神經網路，本節不需要 backward；配對、預測、ID switch 計數，以及偵測的 recall 與 FP 都真實計算。輸出最後一行是程式畫出的 ID 圖的存檔路徑 `artifacts/lesson-19/ids.svg`；上面那張圖，就是頁尾執行紀錄那次執行畫出的這個檔案。

## 收益、代價與失敗範圍

收益：速度預測法讓運動平穩、只短暫漏檢的物件，比較能保住同一個 ID。

代價：每條 track 要多存一個速度；每次呼叫 update 也都要傳入正確的幀號，「速度×間隔」才算得對。急轉、加速、相機移動，或偵測框位置本身的抖動（定位雜訊），都會讓估出的速度不準。正式追蹤器還會用外觀特徵或 Kalman filter 補強，說明見下方摺疊區。本節的完美等速案例，不能證明速度預測解決了所有追蹤問題。

??? note "外觀特徵、Kalman filter 與常見追蹤器"

    - 外觀特徵：另用一個神經網路，把框內的影像變成一串數字，比較兩個框裡的物件長得像不像；兩個物件交叉時，可以靠它分辨誰是誰。代價是要多跑模型、存特徵，還需要有身份標註的資料來訓練。
    - Kalman filter（卡爾曼濾波）：除了估計位置和速度，也估計「這個估計有多不確定」，再依此決定要多相信新的偵測框。代價是要先設定運動和量測各有多少雜訊。

    常見的完整追蹤器例如：

    - SORT：用 Kalman filter 預測位置，再用匈牙利演算法依 IoU 配對。
    - DeepSORT：沿用 Kalman filter 與匈牙利演算法，但配對主要改看外觀特徵的距離（再用 Kalman 預測的位置排除不可能的配對），並讓上次配到的時間越近的 track 越先配。IoU 配對只留在最後一輪，處理兩種 track：剛建立、還在試用期的，以及上一幀還配到、這一幀外觀沒配上的。
    - ByteTrack：分兩輪配對。先拿高分框配所有 track；第一輪沒配到的 track，再只用 IoU 去配低分框。沒配上的低分框當成背景丟掉，也不拿來開新 track。

    本節的 tracker 只取它們共同的核心（先預測位置，再一對一配對），不是這些方法的完整實作。

    多物件追蹤的正式評估常用 IDF1 與 HOTA：IDF1 先把整段影片的軌跡和真實身份一對一對應再計分，著重身份有沒有維持住；HOTA 把偵測準不準和關聯對不對分開量，再合成一個分數。本節只數 ID switch，沒有計算這些分數。

常見錯誤：

- 用偵測框在 list 裡的位置（索引）當 ID：本例為了方便評估，固定讓每幀的偵測框照 A、B 排，所以用索引會碰巧全對；真實偵測器輸出的順序每幀都可能不同，順序本身不代表身份。
- 允許兩條 track 配同一個偵測框：一個框只代表一個物件，不能同時延續兩條 track，其中至少一條接錯了。
- 在空幀清空所有狀態：只要有一幀什麼都沒偵測到，所有 track 就都不見了；之後的物件全被當成新物件重新編號，原本的身份都斷掉。
- 把 tracker 的預測框當成新的偵測框：物件明明沒被偵測到，track 也會靠自己的預測一直配下去，永遠不會過期。
- 用真實身份（GT）參與配對：實際使用時沒有 GT，這樣量出的 ID switch 會好得不真實。

??? note "參考答案"

    **第 1 題**：max_age=1 時，速度預測法的 B 最後在第 3 幀配到 ID2。第 5 幀的 update 一開始先檢查間隔：5−3=2，大於 1，所以 ID2 在配對前就被刪了。速度再準也沒有 track 可接，B 只能開新 ID。ID 只增不減，刪掉的編號不會重用，所以 B 拿到的是 3，不是 2。速度預測法第 5 幀的 IDs 是 `[1,3]`，switch 從 0 變成 1；上一框法仍是 3 次。recall 那一行不變：max_age 只是 tracker 的設定，偵測框沒有變。

    **第 2 題**：max_age 管沒配到的 track 能留多久（壽命）；速度管這一幀要去哪裡找它（運動估計）。兩者是不同的設定：track 一旦被刪，速度再準也接不回來。

## 接上真正的逐幀預測

前面的人工交叉案例固定了偵測框（連漏檢也是人工安排的），兩種方法的差別只來自配對規則；這一段改接第 18 章的真實模型輸出。這個最小 tracker 配對時只看 IoU，不檢查兩個框的類別是否相同。若混入其他類別的預測框，紅矩形的 track 可能接到別類的框上，所以先只留 class 0（紅矩形）的框。`runpy.run_path` 會載入兩節的程式、取得裡面的函式，預設不執行各節的 `main()`；`fit_detector()` 只呼叫一次，模型只訓練一次。

```python
import runpy
import torch
torch.set_num_threads(2)
video = runpy.run_path('lesson_cases/18-video.py')
tracking = runpy.run_path('lesson_cases/19-tracking.py')
model = video['fit_detector']()
tracker = tracking['Tracker'](motion=True, max_age=2)  # motion=True：速度預測法
for result in video['run_stream'](video['synthetic_frames'](), model):
    pred = result['prediction']
    # labels==0 得到一串 True/False，只留下類別 0 的框
    boxes = pred['boxes'][pred['labels'] == 0]
    ids = tracker.update(boxes, result['index'])
    print(result['index'], ids)
```

空幀也照樣呼叫 `update`。本實作在 update 一開始用間隔（幀號差）判斷過期，所以就算跳過空幀，有框的幀拿到的 ID 其實一樣。逐幀呼叫的好處是 tracker 內部的 track 清單每一幀都即時更新。例如下方「影片檔案實測」的結果：ID1 最後在第 1 幀配到，第 2–5 幀都沒有框。逐幀呼叫時，ID1 在第 4 幀就被刪掉（間隔 4−1=3，大於 2）；跳過空幀的話，下一次呼叫要等到第 6 幀，ID1 到那時才會被刪。另外，若 tracker 改成「每呼叫一次 update，沒配到的 track 的 age 才加 1」的寫法（age 指這條 track 連續沒配到的次數），跳過的空幀就不會被算進去，舊 track 會比該留的時間留得更久。之後若一直是空幀、又都被跳過，update 不再被呼叫，age 就不再增加，這條 track 永遠不會過期。

框已經還原成原圖的畫素座標（xyxy）。`ids` 的第 i 個數字對應篩選後 `boxes` 的第 i 個框；若拿去和沒篩選的 `pred['boxes']` 逐一對應（例如用 `zip`），只要有其他類別的框排在類別 0 的框前面，順序就會錯開。`pred['boxes']` 不分類別、照 score 由高到低排；別類的框若剛好都排在後面，`zip` 在 `ids` 用完時就停下，這一幀會碰巧對上，但換一幀就可能錯開，所以一律用篩選後的 `boxes`。

[影片檔案實測](https://github.com/birdhackor/learn_to_yolo/blob/main/artifacts/checks/curriculum/video-file.json)已把同一組真實預測接上這個 tracker：第 0、1 幀回傳 `[1]`，第 2–5 幀是 `[]`（沒有框，也就沒有 ID），第 6、7 幀回傳 `[2]`，其餘是 `[]`。物件連續漏檢的幀數超過 max_age 容許的範圍，重新出現時只能建立新 ID；速度預測沒有修好偵測器的漏檢。這條接線沒有用真實身份（GT）配對計分，所以不能報成新的 ID switch、IDF1 或 HOTA 成績。想重跑這個實際檔案與接線的驗證，需先安裝 `requirements-video.txt`，再執行 `PYTHONPATH=. python scripts/verify_video_file.py`。結果寫在 `artifacts/runs/video-file/result.json`；本段開頭連結的紀錄，是同一支程式加上 `--record artifacts/checks/curriculum/video-file.json` 寫出的同一份報告，自己重跑不必加。換一台電腦重跑，個別幀偵測到的框數可能略有不同，回傳的 ID 也會跟著變；本段寫的是連結的那一次紀錄。
