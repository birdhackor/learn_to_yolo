# clear-tutorial 在 learn_to_yolo 的適用評估

核心可以直接使用；需要的是 YOLO 的具體例子與審閱約定，不必重寫整份 skill。原版已涵蓋機器學習實驗、梯度與參數更新的區別、比較的混淆因素，以及圖解與證據檢查，並非只能用於 FastAPI／SQLModel。

這次保存原版及適用建議，沒有修改教材或重新驗收教材。下列調整是後續使用時應補充的背景，不代表既有章節已通過新的審閱方式。

## 可以直接採用的部分

先展示任務、材料與答案，再引入編號、公式和程式；名詞在推理需要之前說明；一小節追一個主要問題。正文必須解讀看得見的結果，紀錄連結只是查證補充。這些規則很適合從 CNN、ResNet 走到偵測與 YOLO 的閱讀路線。

圖解檢查也可直接採用，而且要檢查「缺少哪些必要圖」，不能只確認已有 SVG 能載入。例如圖說提到紅框中心 `(16,20)`，就必須在實際頁面看見對應紅框，並能辨認座標與圖例；不能以圖檔存在或網站建置成功代替。

實驗證據的規則不需另起一套：`backward()`、`optimizer.step()`、訓練後評測各證明不同的事；低訓練 loss 不等於泛化；技術疑點回查論文或官方實作。原版最後也明確說明，不要求機器學習教材照搬網頁框架的操作步驟。

## 應補充的 YOLO 背景

### 1. 調整讀者背景，不提高門檻

使用者指定的讀者有基本 Python／PyTorch、NN／CNN 理解，接觸過大學微積分、工程數學與線性代數，但不一定熟練。審閱者應依此設定背景，不能把「學過」當成「能立即熟用」。

目前[閱讀路線](../../../docs/learning-path.md)也照顧基礎較少的讀者，不能因為導入 skill 就提高已公布的門檻。必要公式先交代符號、單位與一個數字例子；較長推導可放補充區。順序讀者可以使用前文實際教過的知識，不必每節重新講 Python，也不能假設前文沒有教過的 detector 術語。

### 2. 把座標、張量與圖接起來

YOLO 很容易在「看似懂公式」的地方失去圖像意義。第一次使用時，明確說明軸與順序：`NCHW`、`xyxy`、中心與寬高、`ltrb`；單位是 pixel、normalized 比例還是 feature-map 的格；目前談的是原圖、resize／padding 後的圖，還是特徵圖。

盡量讓同一個框一路連到圖片、target、loss 與 decode，而不是每一步換一組沒有來歷的數字。例如 [9.1 anchor](../../../docs/lessons/09-anchors.md) 的紅框 `[8,12,24,28]`，中心是 `(16,20)`；寬高、anchor、stride 與解碼結果都要在同一個座標約定下解讀。這是局部例子，不要求全書所有實驗使用同一個框。

SVG／動畫應讓讀者看清框、候選點、顏色與箭頭代表什麼；靜態畫面仍能解釋主要概念。視覺驗證要看 Zensical 實際頁面，包含手機版、數學排版與頁面切換，不能只檢查 SVG 原始碼。

### 3. 用演化問題串章節，區分機制示範與效果比較

每個版本回答：沿用哪個起點、遇到什麼問題、主要改了什麼、為什麼這樣改、可能得到什麼好處，以及多了什麼成本或限制。這些關係用自然段落講清楚，不把所有小節硬套成同一張欄位表。

「一次增加一個主要變化」是寫作原則，不代表我們已做控制變因的實驗。網路、候選數、loss 權重、資料或訓練步數若不同，要交代；不能用兩個小示範的分數宣稱某版本較好。論文的結果、我們的實測、對機制的推論應分清楚，也不能把所有 YOLO 名稱說成同一團隊維護的單一直線演化。

[閱讀路線](../../../docs/learning-path.md)已說明版本節不是把每代改動全部疊入同一個模型，這個界線應保留。例如 [12.4 DFL](../../../docs/lessons/12-dfl.md) 直接更新四個 logits，是理解分佈回歸的有效實驗，但不是完整圖片偵測訓練。沒有必要為了符合「可跑」而把每一個手算或機制示範都擴成大型 detector。

### 4. 讓偵測與訓練數字有明確含義

交代 Ground Truth、正負樣本、預測與真值如何配對；不要混用分類正確率、IoU、AP50 與 COCO 常用的 mAP50–95。涉及 AP 時說明 IoU 門檻、precision／recall、插值方式及是否跨類別平均；合成資料的結果不能直接類比 COCO 成績。

訓練示範應指出更新哪些參數、資料與模型在哪個 device、步數與學習率，以及結果支持什麼結論。單一固定樣本的 loss 下降可證明該例子的優化，不證明泛化；GPU 小測試可驗證訓練與 checkpoint 流程，不是正式效能評測。耗時要說清楚是否包含同步、前後處理、存檔與啟動等工作。

數字回查本專案的 [`artifacts/checks/`](../../../artifacts/checks/) 與指定 code commit；不要因為正文說得流暢就略過實際資料，也不要為了修一句話重跑全套 GPU 工作。

## 審閱方式與本專案紀錄的接法

最需要改的是審閱過程。先前的完整頁面閱讀、技術查證與執行紀錄仍可作為各自範圍的證據；除非有符合原版規則的逐段原始紀錄，不能重新標記成「首次閱讀盲讀通過」。

後續使用時，依原版三輪順序執行：

1. 凍結頁面與必要圖的版本，按有意義的單位逐段提供。第一次閱讀者只拿到已讀前文與當前單位，先記錄自己的理解、卡點與缺圖，再開放下一段；不預先給作者摘要、程式答案或先前通過結論。需要獨立 subagent 時，以不繼承作者歷史的上下文開始，並記錄是否提前看過全文。共用檔案系統不是技術隔離。
2. 修正閱讀問題後，由另一位審查者檢查程式、數據、簡化範圍及技術來源。這一輪才能讀完整實作、查論文或執行與疑點相稱的實驗，不要把這些答案提前給第一輪讀者。
3. 技術修正後，另找讀者檢查前後小節的例子與概念銜接；只重查受影響的範圍，不因局部修改重新宣稱全書驗收。

新審閱原始紀錄可另存 `reviews/clear-tutorial/`，包含版本、閱讀單位、當時可見內容、理解、原文卡點、後文何處才釐清，以及修正後複查。這是建議存放位置，本次未產生教材審閱紀錄。保留既有紀錄，不用新摘要覆寫舊問題；未做的閱讀、瀏覽器或執行檢查一律標成未驗證。

真正修改教材時，仍遵守根目錄 [AGENTS.md](../../../AGENTS.md)：同步課文／notebook、更新受影響的執行證據與檢查，不覆寫既有發布 tag。加入 skill 本身不觸發這些教材修改或發布流程。

## 給後續任務的補充 prompt

> 使用 `$clear-tutorial` 時，一併閱讀這份適用評估。讀者有基本 Python／PyTorch、NN／CNN 理解，大學數學學過但未必熟；以實際前文為先備知識。YOLO 章節先讓圖片、框、答案與座標單位對上，再帶入張量、公式與程式。演化章節說清楚起點、改動、理由、收益與代價，分開機制示範、控制比較與正式評測。審閱按照原版逐段揭露方式保存當場理解，並把可讀性、技術查證、前後銜接分輪進行；沒有實際做過的檢查不能宣稱通過。遵守本輪工作範圍，分析或審閱不自動擴成重寫、訓練或發布。
